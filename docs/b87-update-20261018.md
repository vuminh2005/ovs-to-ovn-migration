## Lỗi listener đã xác nhận

Run `20261018-134350` thất bại vì `10.1.0.187:18180` đã được PID `1891963`
của run `20261018-130810` lắng nghe. Log Python ghi `OSError: [Errno 98]
Address already in use`. IP endpoint có trên eth1 của controller.

Thông báo cũ `Cannot bind external endpoint address/port on controller` chỉ
là timeout chờ file JSONL đầu tiên, nên che mất traceback thật. Helper mới
theo dõi process khởi động: process thoát thì ghi checkpoint `FAILED`, exit
code và thông báo lỗi/log ngay; chỉ ghi `RUNNING` cho listener sau khi có
output và process còn sống. Process đang có checkpoint được giữ nguyên,
không tự tạo listener thay thế.

Output controller bổ sung ngày 18/10 đã xác nhận PID `1891963` vẫn là process
trên, nhưng cả `extended-resources.json` ở gốc run lẫn `checkpoints/` đều không
còn. Cleanup cũ chỉ tìm qua checkpoint nên không nhìn thấy process này; không
phải lỗi SSH hay controller không có quyền dừng process. Chưa có bằng chứng
về thao tác nào đã làm mất checkpoint.

Reset đọc cả run phẳng và run có `run-layout.json`, kiểm tra run/config/cmdline
cùng PID, boot ID và start ticks trước khi dừng probe. Nếu checkpoint đã mất,
reset tìm đúng lệnh chạy `scripts/ns_probe.py` của bản dự án đang dùng và config
theo vai trò trong backup root. File config còn tồn tại phải khớp run/output;
nếu toàn bộ thư mục run đã mất, argv tuyệt đối vẫn xác định phạm vi cleanup.
Identity hiện tại được ghi trong evidence `discovered` trước khi gửi SIGTERM
qua pidfd. Không tạo lại checkpoint hay khôi phục resume bằng identity mới.
Checkpoint còn nhưng identity cũ không khớp không được chuyển sang nhánh này.
Kiểm tra cổng tiếp tục chặn destroy nếu process khác vẫn giữ cổng.

Phase 02 cũng kiểm tra khả năng bind endpoint/cổng trước khi tạo VM, để lỗi
cổng bận xuất hiện sớm. Kiểm tra này chỉ bind tạm rồi đóng socket, không mở
listener và không gửi traffic.

## Lỗi tạo VM N-S do user-data quá lớn

Run `20261018-164925` dừng ở phase 04 khi Nova nhận yêu cầu tạo VM N-S đầu
tiên. Payload cloud-init trong log dài 50.474 byte; sau Base64 là 67.300 byte,
vượt giới hạn trường `user_data` 65.535 byte của Nova. File `run_layout.py`
được đưa vào guest để đáp ứng import của `ns_log_transfer.py` làm payload vượt
ngưỡng. Đây là lỗi đóng gói request, xảy ra trước downtime Neutron.

`scripts/validation_placement.py` hiện kiểm tra độ dài của Base64 trước POST.
Nếu vượt ngưỡng, helper giải mã Base64, nén gzip rồi mã hóa lại. Cloud-init hỗ
trợ tự giải nén gzip trước khi xử lý cloud-config. Payload nhỏ giữ nguyên;
payload đã nén không bị bọc thêm lớp gzip. Nếu vẫn quá lớn hoặc Base64 lỗi,
helper báo lỗi cục bộ trước POST, chỉ ghi kích thước và không in nội dung config.

Đã chạy helper với đúng payload trong log: giảm từ **67.300 còn 16.280 byte**,
giải nén khôi phục đủ **50.474 byte** giống từng byte. Regression đi từ
`Extended.add_ns_guest` qua SDK và HTTP đến endpoint HTTP cục bộ mô phỏng giới hạn 65.535,
đối chiếu tất cả file, permission, config và lệnh khởi động sau giải nén.
Không lưu payload/token thật trong bộ test hay ZIP.

Nếu đã dùng bản sửa cleanup listener trước đó, chỉ cần cập nhật
`scripts/validation_placement.py` từ ZIP này. Run lỗi đã tạo một số tài nguyên
và bật listener controller; dùng quy trình reset rồi migration mới bên dưới.

Nguồn đối chiếu:

- [Nova 2024.1 — giới hạn user-data sau mã hóa](https://docs.openstack.org/nova/2024.1/user/metadata.html#user-data).
- [Cloud-init 24.2 — gzip compressed content](https://docs.cloud-init.io/en/24.2/explanation/format.html#gzip-compressed-content).

## Thư mục kết quả

Chỉ run mới được khởi tạo cấu trúc này. Run cũ không có marker tiếp tục đọc,
ghi và resume theo đường dẫn cũ; không tự di chuyển checkpoint lịch sử.

| Vị trí | Nội dung |
|---|---|
| Thư mục gốc | `migration-report.txt`, `migration-report.json`, `run-layout.json` |
| `config/` | Runtime, cấu hình validation/diagnostics, cấu hình Neutron đích |
| `backups/` | Globals/inventory trước migration và vị trí backup MariaDB |
| `resources/` | Danh sách tài nguyên trước/sau, danh sách port VM |
| `checkpoints/` | Ownership, tài nguyên do run tạo, baseline và intent |
| `captures/` | PCAP Group A, state, log capture và cửa sổ đo |
| `evidence/` | Kết quả xác minh và bằng chứng còn lại |
| `logs/` | Log điều phối, DB migration và collector |
| `metrics/`, `task-timings/` | Marker thời gian và timeline task |
| `ns/`, `ns-diagnostics/`, `diagnostics/`, `flows/` | Log probe/capture N-S, observer và flow watch theo vai trò |

Tra đường dẫn của một file trong cả hai kiểu run:

```bash
python3 scripts/run_layout.py path /root/ovs-to-ovn-backup/<run-id> extended-resources.json
```

MariaDB backup vẫn do Kolla quản lý. `backups/mariadb-backup.json` ghi node,
Docker volume `mariadb_backup`, mountpoint và metadata file; cùng thông tin
nằm trong `run_storage.mariadb_backup` của báo cáo JSON. Không sao chép lại
nội dung database vào thư mục run.

Filter được nạp cả ở thư mục gốc và cạnh các playbook con, để helper chạy
từ thư mục khác vẫn lưu được file. Các script chuyển đơn lẻ lên node giữ
nhánh độc lập; các helper cần companion được stage đầy đủ. Capture nhận
diện các helper/cache hợp lệ nhưng vẫn từ chối file ngoài phạm vi/symlink.

## Chạy lại trên lab

Cài đầy đủ ZIP vào `/root/ovs-to-ovn-migration`, giữ inventory và các biến
lab bạn đang dùng. Với run lỗi ở phase 04 này, chạy reset rồi migration mới:

```bash
cd /root/ovs-to-ovn-migration
source /root/venvs/kolla-2024.1/bin/activate

ansible-playbook -i /root/multinode reset-lab-to-ovs.yml \
    -e reset_lab_confirm=true

ansible-playbook -i /root/multinode migrate-to-ovn.yml
```

Giữ các tham số bổ sung nếu lần trước có sử dụng. Reset mới tự dừng listener
cũ khi ownership được chứng minh; không cần hard-code hay kill PID `1891963`.
Evidence cũ được giữ theo mặc định. Các route resume hiện có giữ điều kiện
của b87; run này đã tạo VM và local N-S intent nên không thuộc route retry
chỉ dành cho lỗi tạo VM đầu tiên hoặc capture endpoint chưa khởi động.
